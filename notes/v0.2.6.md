# Pluto CLI v0.2.6

This release fixes iOS builds of apps with large constant tables and lets
`pluto app register` adopt a registration the backend already has. The SDK is
unchanged from v0.2.5.

## Fixes

- iOS baseline and patch builds no longer fail with `bufio.Scanner: token too
  long` when the app bundles a large constant table. WMS hit this after adding
  `pdf`, whose `package:bidi` character table appears as two lines of about
  2.4 MB in the module's bytecode dump. The parser reads the start of each line
  and skips the rest; an over-long library or entry-point line is still
  rejected, and the dump digest still covers every byte.
- `pluto app register` first lists the backend's apps. When the app is already
  registered with the same package, platform, public key, runtime version and
  URLs, for example by a provisioning workflow, it adopts that registration as
  is, display name included, and writes `apps.json` from it without posting. A
  different identity is an error. Previously it posted its own display name and
  the backend refused the change with HTTP 422.
- Pins the same SDK commit as v0.2.5,
  `ddae973f8f431e219725d6cf4b4a5c56e351b376`, from `qeuapp/pluto-sdk`.

## Existing applications

Apps already on v0.2.5 need no new baseline: run `pluto self-update`. Apps on
v0.2.4 or earlier follow the upgrade steps in
[`v0.2.5.md`](v0.2.5.md#existing-applications).

## Validation and limits

The Go suite, CLI dependency boundaries, deterministic SDK export and release
packaging passed.

An end-to-end iOS rehearsal ran WMS on a physical iPhone 14 Pro against the
QEU backend (`qeuapp/backend` PR #639), run locally, using this release's code
and the SDK above:

- the new runtime family was registered at baseline build time, and the
  device's status reports were accepted from its first launch;
- the first patch passed trusted Mac verification and was published;
- `next_launch` staged a patch and started it on the next cold launch;
- `live` swapped a patch into the running app in about three seconds, without
  a process restart, and the app reported healthy;
- `paused` limited the device to `policy.json`;
- a rollback to the bundled baseline applied on the next cold launch, and the
  device reported healthy.

That run used a personal Apple team and a separate bundle identifier, not the
App Store build. Setup notes from it:

- Pass the app's dynamic interface on every iOS baseline and patch build, for
  WMS `--dynamic-interface .pluto/wms_host_interface.yaml`. The CLI does not
  record it per target, and a host built without it crashes at launch.
- An engine whose Dart sources are split across directories needs
  `verifier_source_root` in the registry's `publication.json` for trusted
  verification.
- `pluto install --device` takes the CoreDevice identifier that the error
  message lists, not the UDID.

CLI archives target `darwin-arm64`, `darwin-amd64`, and `linux-amd64`. Each
contains only `pluto` and `THIRD_PARTY_NOTICES.txt` and ships with its checksum
and signature using the existing release trust root.
