# Pluto CLI v0.2.8

This release lets a QEU super-admin run Pluto on an environment backend with
their own account, and lets the backend create each app's release key. The SDK
is unchanged from v0.2.5. There is no v0.2.7.

## Sign in with a QEU admin account

- `pluto login` opens a one-time sign-in page in your browser. The CLI serves it
  on `127.0.0.1`. Sign in with a QEU super-admin (`is_admin`) account; the tab
  closes itself when it is done. If no browser opens, the command prints the
  link. The page accepts requests only from itself, and the password goes from
  it to the CLI and on to the backend only.
- `pluto login --no-browser` prompts in the terminal instead, for the email or
  phone (or `--email`) and for the password without echo. No command takes a
  password as a flag.
- The session is saved owner-only as `admin-session.json` in the environment
  registry. Every command for that environment uses it and renews the access
  token shortly before it expires, including commands that run for a long time,
  such as an iOS `pluto patch` or `pluto logs --follow`. Targets that share a
  registry and backend share one sign-in.
- Without a session, commands use the registry's `operator.token` as before. If
  a renewal fails and an `operator.token` exists, they use it and warn once.
- `pluto logout` ends the session on the backend and removes the file.

## The backend creates release keys

- `pluto app register` registers a target whose `updates.public_key` is still
  `BASE64_ED25519_PUBLIC_KEY` (or empty) without a key. The backend creates the
  signing key, keeps it, and returns the public key, which the CLI writes into
  the target file, changing only that line. Commit it. If the backend already
  has the app, its key is adopted the same way.
- `pluto app register` also works without `--config`, and asks which target to
  register when the app has several.
- The `updates.public_key is not configured` error and `pluto doctor` now point
  at `pluto app register`.

## Other changes

- `pluto dashboard` opens the browser with `xdg-open` on Linux.

## Backend requirement

Admin sign-in and backend-created keys need the QEU backend from
`qeuapp/backend` PR #673, which DEV runs. Against an older backend, use the
registry's `operator.token` and a public key the backend already holds.

## Existing applications

No new baseline is needed: run `pluto self-update`. Registries that hold an
`operator.token` keep working without signing in.

## Validation and limits

The Go suite, including a race-detector run of concurrent session renewal, the
CLI dependency boundaries, deterministic SDK export and release packaging
passed. An end-to-end test against a TLS backend fake signs in through the
browser page, registers a new app whose key the backend creates and writes into
the target file, and signs out. The sign-in page was exercised in Chromium: a
wrong password shows the backend's error, and a successful sign-in saves the
session and closes the tab.

This release was not rehearsed against DEV with a real admin account. iOS
patches still need the trusted Mac's verifier credentials (`publication.json`,
`verifier.seed`, `verifier-trust.json`); an admin sign-in does not replace them.

CLI archives target `darwin-arm64`, `darwin-amd64`, and `linux-amd64`. Each
contains only `pluto` and `THIRD_PARTY_NOTICES.txt` and ships with its checksum
and signature using the existing release trust root.
