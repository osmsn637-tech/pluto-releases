# Pluto CLI v0.3.0

This release lets an iOS app keep its own native channels and platform views
under Pluto, makes iOS verification work on an installed engine, and fixes
environment registrations, onboarding and device checks. It pins an SDK with a
new iOS API, so apps need a new baseline. There is no v0.2.10.

## iOS apps with their own native code

- A Pluto app cannot own its Flutter engine: the runtime supervisor starts
  every engine, the first one and each in-process replacement. Apps whose
  `AppDelegate` built channels and platform views on an engine of their own
  had no supported path.
- `pluto_ios` now has `PlutoHostPlugins.register`. Set it once in
  `application(_:didFinishLaunchingWithOptions:)`; the supervisor calls it with
  the plugin registry of every engine it starts, right after the generated
  plugins:

  ```swift
  PlutoHostPlugins.register = { registry in
    let registrar = registry.registrar(forPlugin: "AppNative")!
    // registrar.messenger() replaces flutterEngine.binaryMessenger
  }
  ```

  Scene URL and user-activity events reach the app through
  `registrar.addSceneDelegate`, and `SceneDelegate` stays
  `class SceneDelegate: FlutterSceneDelegate {}` until `pluto integrate ios`
  writes Pluto's.
- `pluto integration inspect` lists every `ios/Runner` Swift line that creates
  or uses an app-owned engine, and its report explains the move line by line.
  A custom `SceneDelegate` is told where its code goes. `pluto integration
  verify` fails while the app still owns an engine.

## iOS verification and the installed engine

- A published engine bundle ships the Dart checkout as plain files without the
  Dart SDK's own Git metadata, so the verifier's `git status` read the Flutter
  checkout and refused with "verifier source checkout has tracked
  modifications". iOS baseline registration and patch verification failed on
  every installed engine. The verifier now re-hashes the bundle, requires the
  published catalog entry, and uses its Flutter revision and tree digest as
  the toolchain identity. Locally built engines are inspected as before.
- That `git status` also refreshed `flutter/.git/index`, so the next build
  failed with an engine bundle tree SHA-256 mismatch. The index is now one of
  the paths the install snapshots.
- iOS inspection and `pluto integration verify` use the pinned engine's
  Flutter, which every iOS build uses, instead of the `flutter` on `PATH`. A
  different Flutter on `PATH` no longer makes `baseline build` fail its parity
  check, and `baseline build` names the checks that fail.

## Environment registrations and onboarding

- Re-running `pluto app register --config FILE` refreshes the target's record
  from the backend and the target file and moves it to the SDK this CLI pins,
  printing what changed. Records left by an older CLI no longer keep onboarding
  pinning `pubspec.yaml` to the old SDK, or fail with "registry already
  records application ... differently".
- `pluto app pin` accepts `--config` and changes the environment registry.
- `pluto app register` accepts an iOS target with `build.flavor` (its Xcode
  scheme); only an Android flavor selects a target.
- Onboarding a target that already exists keeps its `environment`,
  `registry`, iOS build flavor, launch check and build options instead of
  rewriting the file from the registry record, and no longer writes
  `flavor: null`.
- `--config` no longer passes an iOS `build.flavor` on as an Android
  `--flavor`, which made `pluto install --config` refuse iOS targets.

## Builds and devices

- When `pluto install` rebuilds a baseline, it keeps the dynamic interface
  archived with the latest baseline, as patch builds do, instead of the SDK
  default.
- `pluto device state` finds builds that are not development-signed
  (TestFlight, ad hoc, App Store); `devicectl` hides them unless asked.

## SDK

The pinned SDK is `5442c9748f68f4bc2794a7ad88b7fbfe97a6d51a`. Pin it as the
`pluto` ref in `pubspec.yaml`, or re-run `pluto app register` and onboard.

## Existing applications

Run `pluto self-update`, then `pluto engine install --repair --yes` once. Run
`pluto app register --config FILE` for each environment target. iOS apps whose
`AppDelegate` owns a Flutter engine follow the inspection report's Engine
ownership section first. Then build a new baseline and reinstall it.

## Validation and limits

The Go suite, the SDK's Swift package build, deterministic SDK export and
release packaging passed. The verifier identity and the engine digest were
checked on the installed published bundle, including after a `git status`. The
QEU iOS app on `dev` was migrated to `PlutoHostPlugins`, integrated, verified
and built into a signed baseline with this CLI. It was not run on a device, so
its native channels, CallKit wake without a scene and cold-start deep links are
untested, and its baseline was not registered with a backend.

CLI archives target `darwin-arm64`, `darwin-amd64`, and `linux-amd64`. Each
contains only `pluto` and `THIRD_PARTY_NOTICES.txt` and ships with its checksum
and signature using the existing release trust root.
