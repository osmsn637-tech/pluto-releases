# Pluto CLI v0.2.5

This release runs operations through environment backends, adds a
backend-controlled update policy on both platforms, and makes iOS updates quiet
by default.

## Breaking changes

- The local backend mode is removed: `native.json` mode, `pluto serve`/`stop`,
  the `pluto-serve`, `pluto-service` and `pluto-logs` companions, and the local
  delivery filter are gone. Operate through an environment target, either
  `--config FILE` or a default target in `pluto.yaml` that names its
  environment and registry. See `docs/environments.md`.
- Backend routes live under `/v1/pluto`: operator, verifier, dashboard, health
  and device status. An environment's status URL must be exactly its update
  origin plus `/v1/pluto/client/status`.
- Operational commands require the application's Git worktree to be on `main`,
  `master`, or a branch approved in the app's `pluto.branch-policy.json`.

## Backend update policy (iOS and Android)

- Devices read `<update URL>/policy.json` during every update check. It sets:
  - `activation`: `live` or `next_launch`;
  - `updates`: `on` or `paused`;
  - a check interval between 1 minute and 1 day.
- `next_launch` keeps a verified release staged until the next cold launch,
  without the in-app swap (iOS) or managed restart (Android).
- `paused` skips update checks. Paused devices also miss rollbacks, and a
  release that was already staged still starts on its next cold launch.
- Defaults: iOS `next_launch`, Android `live` (the existing managed restart).
  A missing policy uses these defaults; a failed or malformed read keeps the
  last policy the device saw. Android stores it, so a restarted app keeps it;
  iOS starts each launch from its default until the first check. The policy only times or pauses signed releases
  and never selects code, so it is not signed.
- New SDK API: `Pluto.policy`, `Pluto.policyChanges`,
  `PlutoUpdateCheckStatus.paused`, and the `coldLaunchRequired` failure codes
  `policy_next_launch` and `policy_updates_paused`. Apps that switch over
  `PlutoUpdateCheckStatus` must handle `paused`.
- Operators change the policy on the dashboard's Update policy card, or with
  `GET`/`POST /v1/pluto/operator/apps/<app>/policy`.

## iOS

- `pluto_ios` ships a privacy manifest. It declares UserDefaults (`CA92.1`),
  system boot time (`35F9.1`) and file metadata (`C617.1`), plus update
  diagnostics that are neither linked to the user nor used for tracking.
- Native update screens default to neutral text ("Loading…", "Please restart
  the app"). Pluto branding stays hidden unless `ShowsPlutoBranding` is set.

## Environments and registration

- `pluto app register --config FILE` registers a target on its environment
  backend with the target's existing public key, then records it in the
  registry's `apps.json`. It never generates keys; an identical re-run is a
  no-op and a conflicting record is an error.
- Baselines register with the environment backend right after
  `pluto baseline build` and `pluto install`, where a failure is a warning,
  and before any verifier-contract work in `pluto patch`. Devices' status
  reports are accepted from the first launch. The first iOS patch on a new
  runtime family no longer fails while reading its verifier contract.
- Opaque operator tokens of at least 32 bytes without whitespace are accepted.
- `pluto dashboard open` and `pluto logs` work against the environment
  backend after checking its health and the app's identity.
- Pins SDK commit `ddae973f8f431e219725d6cf4b4a5c56e351b376` from `qeuapp/pluto-sdk`.

## Existing applications

After updating the CLI, pin each app's registry to the new SDK, re-run
integration and rebuild its baselines; the SDK's native code changed on both
platforms. Keep the registered app IDs and public keys; do not create
replacement signing keys:

```sh
pluto self-update
pluto app pin APP_ID --package-ref ddae973f8f431e219725d6cf4b4a5c56e351b376
pluto integration inspect --app APP_ID --platform android
pluto integrate android --apply
```

Use `--platform ios` and `pluto integrate ios --apply` for the separate iOS
app ID. Handle `PlutoUpdateCheckStatus.paused` in update controllers, then
build a new baseline for each platform. iOS apps without a policy on their backend now wait for the
next launch instead of swapping code while open.

## Validation and limits

The Go suite, CLI dependency boundaries, deterministic SDK export, release
packaging, Dart analysis and tests (62), native iOS tests (137) and Android
native unit tests (126) passed.

An end-to-end Android rehearsal ran this release's CLI and the Git-pinned SDK
on a physical Xiaomi 2410FPCC5G (Android 16) against the QEU backend
(`qeuapp/backend` PR #639), run locally:

- `pluto app register` registered the app; a re-run changed nothing and a
  conflicting record was refused.
- The baseline was registered at build time, and the device's status reports
  were accepted from its first launch, before any patch.
- `live`: patches swapped in through the managed restart once the app was in
  the foreground.
- `next_launch`: a patch was downloaded and staged but not activated, then
  started on the next cold launch.
- `paused`: the device requested only `policy.json`; no release or artifact
  was fetched until updates resumed.
- `pluto release rollback --to baseline` restored the bundled baseline and the
  device reported healthy.

The rehearsal found two defects, both fixed in this release:
`pluto app register --config` was rejected by the command dispatcher, and
Android reported the default policy after a cold start into a new release.

iOS was not run on a device for this release. Its policy, presentation and
privacy-manifest changes are covered by Dart and native tests only; the first
iOS patch on a new runtime family still needs a run against an environment
backend with the app's signing key and a trusted Mac verifier.

CLI archives target `darwin-arm64`, `darwin-amd64`, and `linux-amd64`. Each
contains only `pluto` and `THIRD_PARTY_NOTICES.txt` and ships with its checksum
and signature using the existing release trust root.
