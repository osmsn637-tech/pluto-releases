# Pluto CLI v0.2.9

This release fixes iOS device detection on Xcode 26 and the engine check that
failed after every iOS build, adds `pluto verifier register`, and pins an SDK
whose Android runtime no longer crashes builds without Pluto configuration.

## iPhones are found on Xcode 26

- Xcode 26's `devicectl` reports devices in its older JSON layout, which the
  CLI did not read, so every phone looked unavailable and not physical.
  `pluto install`, `pluto device list` and `pluto doctor` now read both
  layouts.
- `pluto install --device` also accepts the hardware UDID, as well as the
  CoreDevice ID or the device name.

## iOS builds no longer break the engine check

- The pinned Flutter rewrites `engine.stamp`, `engine.realm` and `lockfile`
  and re-runs `pub get` in `flutter_tools` on every run, so the next command
  reported `installed engine bundle tree SHA-256 mismatch`.
- `pluto engine install` now keeps a verified copy of those paths at install
  time and checks it instead of the live files. Every other file is still
  checked against the published digest, which is unchanged.
- Existing engine installs do not have that copy yet. Run
  `pluto engine install --repair --yes` once after updating.

## Register the iOS verifier Mac in one command

- `pluto verifier register --config FILE` creates this Mac's verifier key,
  registers its public half with the environment backend, and writes
  `publication.json`, `verifier-<id>.seed` and `verifier-trust.json`
  owner-only into the registry. The private key never leaves the Mac, and the
  backend needs no redeploy.
- `--key-id` defaults to `mac-<computer name>`. The backend refuses an ID that
  is already registered, and the command refuses to replace an existing
  `publication.json`.

## SDK: Android builds without `pluto.xml`

- The pinned SDK is `96c94fa1e3656d5b5f8ef24864711141b2e55312`.
- `PlutoActivity` threw `missing Pluto string resource pluto_app_id` in any
  variant built without `pluto.xml`, such as a store flavor that shares
  `MainActivity`. The runtime now logs that updates are disabled and runs as
  plain Flutter. A partly present `pluto.xml` still fails loudly.
- Apps pick it up by pinning `ref: 96c94fa1e3656d5b5f8ef24864711141b2e55312`
  for `pluto` in `pubspec.yaml` and running `flutter pub get`.

## Backend requirement

`pluto verifier register` needs the QEU backend from `qeuapp/backend` PR #706,
which DEV runs. Everything else works against the v0.2.8 backend.

## Existing applications

Run `pluto self-update`, then `pluto engine install --repair --yes`. Updating
the SDK pin changes the app's dependencies, so build a new baseline and
reinstall it.

## Validation and limits

The Go suite, the Android runtime unit tests, deterministic SDK export and
release packaging passed. Device detection is tested against real Xcode 27
`devicectl` output converted to the Xcode 26 layout; the engine check is tested
on synthetic bundles, including a full install followed by the rewrites one
Flutter build makes. Neither was run on a real Xcode 26 Mac or with a full iOS
build. `pluto verifier register` was tested against a fake backend; DEV serves
the endpoint but no verifier has been registered through it yet.

CLI archives target `darwin-arm64`, `darwin-amd64`, and `linux-amd64`. Each
contains only `pluto` and `THIRD_PARTY_NOTICES.txt` and ships with its checksum
and signature using the existing release trust root.
